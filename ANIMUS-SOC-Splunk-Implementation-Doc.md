# ANIMUS 1.0 — TEMPLAR SOC
## Implementation Doc: Splunk App (Investigation Environment Only)
**Revision 3 — Dashboard removed, System Status removed, RBAC + live publishing model added**

**Target platform:** Splunk Enterprise 10.4.0
**Source of truth:** ANIMUS registration portal (Breach_Protocol landing page) — the only visual reference
**Supersedes:** every prior version of this doc, the original Data Contract / State Machine /
Master Implementation Prompt, the custom React SOC direction, and the earlier Splunk theme passes
that included a Dashboard or System Status page. All retired.

---

## 1. Architecture — Read This First

**The Splunk app is not the game. It is the investigation environment the game happens inside.**

The CTF Portal (external, out of scope for this doc) owns everything gameplay-related: the 7
incident descriptions, investigation questions, answer submission and validation, scoring,
progress tracking, timeline reconstruction, and challenge navigation.

The Splunk app owns nothing gameplay-related. It is a themed enterprise investigation platform a
player happens to be doing forensics inside. It never knows which case a player is on, never
tracks progress, never validates anything.

**Player flow:** CTF Portal (read case, read question) → Splunk App (investigate using native
Search, Alerts, Threat Intelligence) → CTF Portal (submit answer, see score).

**Do not build in Splunk, under any circumstance:**
- Case list / case selector, question forms, answer submission
- Progress bars, completion state, scoring, leaderboards
- Fragment cards, reconstruction UI, team names or per-team identifying UI
- KPI dashboards, executive summaries, operational overviews, mission boards, statistics pages,
  decorative widgets
- A Dashboard landing page of any kind
- A System Status / System Health page of any kind

If a design idea starts to resemble any of the above, it belongs in the CTF Portal, not here.

---

## 2. What Changed in This Revision

- **Dashboard page removed entirely.** No landing dashboard, no KPI/status widgets, no "operation
  framing" screen. The player should land directly inside an investigation platform.
- **System Status page removed entirely.** Not optional, not minimal — cut.
- **Navigation reduced to three functional areas:** Investigation Console, Alerts, Threat
  Intelligence.
- **Default landing page after login is the Investigation Console** (native Search, themed and
  relabeled), not a dashboard.
- **RBAC model formalized:** organizers hold Splunk super-admin; each of 15 player accounts holds
  a strictly read-only role.
- **Live publishing + notification mechanic specified:** how the admin team actually pushes
  Alerts and Threat Intelligence during the competition, and how players get notified in real
  time inside the app.
- **Full custom-app packaging steps added:** the concrete file/folder layout and install steps to
  ship this as a themed Templar Order Splunk app.

## 4. Screens

### 4a. Investigation Console (`search` — native Splunk Search & Reporting)
**This is the product.** Players spend almost the entire competition here.

- Preserve native Splunk Search completely: SPL editor, search execution, results grid, Timeline,
  Statistics, Raw Events, Field sidebar. None of this is rebuilt.
- Rename "Search & Reporting" to **Investigation Console** at the nav/label level only.
- Theme visually only — dark palette, monospace type on timestamps/IDs/results, crimson reserved
  for scope-violation/error states from any custom SPL macros or lookups. Never decorate in ways
  that reduce table/results legibility.
- Players write real SPL against real indexes, scoped via standard Splunk RBAC (index/role
  permissions) — not a custom scope-enforcement layer.
- Set as the default post-login landing view (Section 3).

### 4b. Alerts (`alert_list` — native Splunk Alerting)
Represents operational detections generated by the Templar SOC — distinct from Threat
Intelligence. Themed only, no custom logic beyond what's described in Section 6.

Example alert names to seed (content decision, not a UI-building task):
- Suspicious PowerShell execution
- Lateral movement detected
- Failed authentication burst
- Beacon activity observed
- Registry persistence detected

Alerts should read as natural operational detections a real SOC would generate, and can double as
investigative red herrings or hints per organizer content design.

### 4c. Threat Intelligence (`templar_threat_intel`)
The primary live communication channel during the competition. A Dashboard Studio view rendering
organizer-published bulletins as Templar-branded intelligence updates (monospace meta-labels,
crimson-on-black severity tags).

Bulletin types: IOC Updates, Operational Advisories, Malware Intelligence, Campaign Updates,
Infrastructure Changes, Tactical Guidance, Emergency Broadcasts.

This is a broadcast/flavor + operational-pressure mechanic — nothing here feeds the CTF Portal or
affects scoring/validation.

## 5. RBAC Model

Two roles, no more.

| Role | Who | Splunk role basis | Capabilities |
|---|---|---|---|
| **Templar Admin** ("Mission Control") | Organizers | Splunk built-in `admin` (or a custom `templar_admin` role inheriting `admin`) | Full super-admin: create/edit knowledge objects, write to KV Store collections, manage saved searches, manage users/roles, publish Alerts and Threat Intel, monitor sessions |
| **Templar Player** | 15 player accounts | Custom role `templar_player` | Read-only: `search` capability against the team's assigned index/indexes only (`srchIndexesAllowed` / `srchIndexesDefault` scoped per team via RBAC — not app logic); read access to the `templar_alerts` and `templar_threat_intel` KV Store collections; **no** write/edit/delete capability on any knowledge object, KV Store collection, saved search, or dashboard |

Concrete role definition guidance for `templar_player` (via `authorize.conf` / Splunk Web →
Settings → Roles):
- Inherit from `user`, **not** `power` or `admin`.
- Remove `schedule_search`, `edit_*`, `admin_all_objects`, and any write-type capabilities.
- Set `srchIndexesAllowed` to only the indexes relevant to that team's investigation data.
- Grant read on `templar_alerts` and `templar_threat_intel` collections explicitly via
  `collections.conf` / object permissions (Section 6) — do not rely on default KV Store
  permissions, which can be broader than intended.
- If all 15 accounts share one team/dataset scope, one `templar_player` role is enough; if teams
  are isolated per-index, either create one role per team (`templar_player_team01`, etc.) or keep
  one role and enforce isolation via per-user index ACLs — this is an admin/ops decision outside
  this doc's scope, but the role must never grant write capability regardless of which path is
  chosen.

Player accounts should **never** be able to reach a Mission Control view, edit an alert, or write
to a KV Store collection — this is enforced at the platform/role level, not by hiding a nav link.
A hidden-but-reachable admin URL is not an acceptable control.

## 6. How the Admin Team Publishes Alerts and Threat Intelligence

Both Alerts and Threat Intelligence use the same underlying mechanism so there is only one
publishing workflow for organizers to learn and operate live, under time pressure. Favor boring
and reliable over clever.

### 6a. Data layer — KV Store
Two KV Store collections, defined in `collections.conf`:

```
# default/collections.conf
[templar_alerts]
field.timestamp = time
field.title = string
field.severity = string
field.body = string
field.status = string

[templar_threat_intel]
field.timestamp = time
field.title = string
field.category = string
field.severity = string
field.body = string
```

Permissions on both collections (via `default.meta` / `local.meta` or the Splunk Web permissions
UI):
- **Read:** `templar_player` role (and admin)
- **Write:** admin / `templar_admin` role only

This is what actually enforces "players read-only, admin full control" at the data layer — not
just at the UI layer.

### 6b. Publishing interface — Mission Control
A single admin-only Dashboard Studio view (`templar_mission_control`), **not present in
`default.xml`** so it never appears in player navigation, and additionally permission-restricted
to the admin role via object ACLs (so it isn't reachable even by a guessed URL on a player
account).

Mission Control contains simple input fields (title, body, severity/category, type =
alert-or-intel) and a publish action. Two implementation options, in order of recommended
simplicity:

1. **Direct KV Store REST call from the dashboard** (recommended). Dashboard Studio supports a
   button/input driving a POST to Splunk's built-in KV Store REST endpoint
   (`/services/storage/collections/data/<collection_name>`) using the admin's own authenticated
   session. No custom backend service required — this is native Splunk REST, just called from an
   in-app form. Requires a small piece of `app.js` (or a Dashboard Studio "Source" input action)
   to construct and fire the POST with a CSRF/session token, which Splunk Web already provides to
   authenticated pages.
2. **Saved-search / lookup-file fallback.** Organizer edits a CSV lookup (`templar_bulletins.csv`)
   via Splunk Web's built-in lookup editor, and a scheduled saved search on a short interval
   (e.g. every 1 minute) syncs new/changed rows into the KV Store collections. Slightly higher
   latency, but requires zero custom JS/REST work and is easier to operate under stress — a
   reasonable fallback if option 1 proves fragile in testing.

Either way, the **native Splunk Alerting UI is not used to author alert content** — Alerts shown
to players (Section 4b) are themed, curated entries in `templar_alerts`, not live SPL-triggered
alerts. This keeps the publishing workflow identical for both Alerts and Threat Intel and avoids
depending on real detection logic firing correctly live during a competition.

### 6c. Additional Mission Control capabilities (organizer-facing only)
- Publish Threat Intelligence bulletin
- Publish Operational Alert
- Broadcast Emergency Message (a `severity = "emergency"` record in `templar_alerts` or its own
  small collection, styled distinctly — e.g. full-width crimson banner)
- Update/annotate IOC list entries (just additional bulletin records tagged `category = "ioc"`)
- Monitor connected sessions — Splunk's own `_internal` index / Activity: Monitoring Console
  already provides active-session visibility; no need to rebuild this, just point organizers at
  the existing Splunk Monitoring Console if session visibility is wanted.

## 7. Live Notifications

A real gameplay mechanic: when the admin team publishes a new Alert or Threat Intel bulletin,
every logged-in player should see a themed in-app notification promptly, not have to
manually refresh the page.

**Recommended implementation:** lightweight polling from `app.js` (auto-loaded on every page
while the app is active), not a websocket or external service — keeps everything inside the
Splunk app, no added infrastructure.

- On an interval (e.g. every 15–20 seconds), `app.js` issues a read-only GET against the
  `templar_alerts` and `templar_threat_intel` KV Store REST endpoints, sorted by `timestamp`
  descending, limit 1.
- Compare the latest record's `_key`/`timestamp` against the last-seen value stored client-side
  (`localStorage`, scoped per browser/session — acceptable here since this is a real production
  Splunk app, not a sandboxed artifact).
- If newer, render a themed notification element fixed to a corner of the viewport:
  - `NEW THREAT INTELLIGENCE AVAILABLE` / `Click to View`, or
  - `HIGH PRIORITY ALERT` / `Investigation Recommended`
- Style it as an internal enterprise system notification — sharp corners, 1px crimson border,
  monospace type, brief glow on appearance, no browser-toast styling, no rounded corners, no
  bounce/slide animation (restrained motion per Section 8).
- Clicking navigates the player directly to the Alerts or Threat Intel view as appropriate.
- Read access for this polling call is covered by the `templar_player` role's read grant on both
  collections (Section 6a) — no elevated privilege needed client-side, which is important since
  this JS runs in the player's own authenticated browser session.

This satisfies the "every logged-in player immediately receives a notification" requirement
without introducing a dependency outside native Splunk mechanisms.

## 8. Visual Identity

Continue using the ANIMUS registration portal as the only visual reference — no generic
cybersecurity dashboard aesthetics.

| Element | Rule |
|---|---|
| Surfaces | Near-black void (`#05060a`), deep charcoal panels (`#0d1117`) — one dark base only |
| Accent | Single restrained crimson (`#ff1e3c` family), used sparingly, glow on text only, never on fills |
| Typography | Monospace, all-caps, wide tracking, `SNAKE_CASE` labels — `INVESTIGATION_CONSOLE`, `ALERTS`, `THREAT_INTEL` |
| Edges | Sharp corners, thin 1px separators — no rounded cards |
| Motion | Minimal — glow/opacity transitions only, no movement, no bounce |
| Avoid | Neon effects, RGB lighting, cyberpunk styling, oversized dashboard cards, decorative charts, unnecessary widgets |

**Primary design goal:** players should forget they are using Splunk and believe they've entered
the genuine internal SOC of the Templar Order. Investigation over presentation, realism over
spectacle, operational pressure over visual complexity.

## 9. Custom App Packaging — How to Implement This as a Templar-Themed Splunk App

### 9a. App directory layout

```
templar_soc/
├── app.conf                         (in default/)
├── appserver/
│   └── static/
│       ├── app.css
│       ├── app.js                   (theming hooks + live notification poller, Sec. 7)
│       ├── appIcon.png              (36x36, app switcher)
│       └── appIconAlt.png           (dark-mode variant)
├── default/
│   ├── app.conf
│   ├── collections.conf             (KV Store schema, Sec. 6a)
│   ├── data/
│   │   └── ui/
│   │       ├── nav/
│   │       │   └── default.xml      (Sec. 3)
│   │       └── views/
│   │           ├── templar_threat_intel.xml   (Dashboard Studio, Sec. 4c)
│   │           └── templar_mission_control.xml (Dashboard Studio, admin-only, Sec. 6b)
│   └── data/ui/nav/                 (as above)
├── metadata/
│   ├── default.meta                 (default object permissions)
│   └── local.meta                   (per-object overrides — KV Store read/write split, Sec. 6a)
└── bin/                             (optional — only needed if a custom REST endpoint is added
                                       instead of calling the native KV Store REST API directly)
```

### 9b. `app.conf` essentials

```ini
# default/app.conf
[install]
is_configured = true

[ui]
is_visible = true
label = Templar SOC

[launcher]
author = Templar Order
description = Templar Order internal Security Operations Center
version = 1.0.0
```

### 9c. Install steps
1. Create the folder structure above under a working directory named `templar_soc`.
2. Add `app.css` / `app.js` (Section 8b / Section 7) to `appserver/static/`.
3. Add `default.xml` (Section 3) to `default/data/ui/nav/`.
4. Add `collections.conf` (Section 6a) to `default/`.
5. Build `templar_threat_intel` and `templar_mission_control` as Dashboard Studio views (built in
   Splunk Web once the app is installed and reloaded — their XML/JSON definitions are then saved
   back into `default/data/ui/views/` for version control).
6. Set object permissions in `local.meta` so:
   - `templar_mission_control` view is readable/writable only by admin.
   - `templar_threat_intel` view and both KV Store collections are readable by `templar_player`,
     writable only by admin.
7. Replace `appIcon.png` / `appIconAlt.png` with the Templar mark.
8. Copy the completed `templar_soc` folder to `$SPLUNK_HOME/etc/apps/templar_soc` on the Splunk
   instance (or install as a packaged `.spl`/`.tar.gz` via Splunk Web → Manage Apps → Install app
   from file).
9. Restart Splunk Web (`splunk restart splunkweb`) or perform a full restart if `collections.conf`
   or `app.conf` changed — nav/CSS-only changes typically just need a browser refresh.
10. Create the `templar_player` role and the 15 player accounts (Section 5), confirm read-only
    behavior by logging in as a test player account and attempting a write against a KV Store
    collection — it should fail.
11. Confirm the app's home/default view lands on Investigation Console, not a launcher page —
    set `templar_soc` as the default app for player accounts (per-user or per-role default app
    setting) so login goes straight into it.

### 9d. Login
Themed per Section 8, with copy such as: *"Security Notice — Unauthorized access detected.
Compromised privileged credentials originating from the Domain Controller incident remain active.
All sessions are logged."* Full visual theming here is a platform-level surface, not fully
app-scoped — confirm feasibility on your instance before treating it as guaranteed (Section 10,
Open Question 2).

## 10. Open Questions to Confirm Before Build

1. **Modern Navigation** — is Splunk 10.4's side-panel nav enabled on your instance, or classic
   top-bar-plus-left-rail chrome? Determines which selector set in `app.css` actually applies.
2. **Login-page theming** — hard requirement or stretch goal? May need `web.conf` login banner
   settings rather than a clean CSS injection; spike before committing design time.
3. **Mission Control publish mechanism** — confirm direct KV Store REST call (Section 6b, option
   1) vs. the lookup/saved-search fallback (option 2), based on who's operating it live and how
   comfortable they are debugging JS/REST under time pressure.
4. **Team isolation granularity** — one `templar_player` role for all 15 accounts sharing a
   dataset, or per-team roles/index ACLs? Affects `authorize.conf` setup in Section 5.
5. **Session monitoring** — confirm whether organizers will use Splunk's built-in Monitoring
   Console for "connected sessions" visibility (recommended) or whether a custom view is actually
   wanted despite the added build/maintenance cost.
